# Agentic Knowledge Search

社内文書を、AIが**検索を計画し、足りなければ検索し直してから**出典つきで答える「エージェント型RAG」のデモです。
題材は架空の会社「Contoso Japan 株式会社」の社内規程・FAQ です。

> 🚧 開発中（2026年12月公開予定）。デモURL・評価結果・動画は公開時に追記します。

## 特徴

| | 単純なRAG | このプロジェクト（エージェント型RAG） |
| --- | --- | --- |
| 検索 | 質問をそのまま1回だけ検索 | 質問を論点に分解して検索を計画 |
| 足りないとき | そのまま答える（推測が混ざる） | 根拠が足りるか判定し、足りなければ検索し直す |
| 検索方式 | ベクトル検索のみが多い | キーワード＋ベクトルのハイブリッド検索 |
| 根拠 | 示さないことが多い | 出典番号つきで回答、根拠がなければ「確認できない」 |
| 見える化 | なし | 振り分け・計画・検索・判定の流れを画面に表示 |
| 速度と費用 | 速くて安い | 自動モードで、簡単な質問だけ単純なRAGに回して両立。検索は並列化 |
| 判定 | - | 振り分けと「根拠が足りるか」の判定に Azure OpenAI Decisions API（2026年10月GA）を使える |
| 品質 | 感覚で確認 | 40問の評価セットで正答率・出典の正しさ・速度・トークン数を比較 |

## 構成

```
ユーザー → React（Static Web Apps）→ FastAPI（Container Apps）
                                        ├─ Azure OpenAI（gpt-4.1-mini / text-embedding-3-small）
                                        └─ Azure AI Search（ハイブリッド検索）
架空の社内文書 → 取り込みスクリプト（分割→ベクトル化→登録）→ Azure AI Search
GitHub Actions ＋ Bicep で自動デプロイ
```

自動モード（`/api/ask` の既定）は、最初に質問を「単純」か「複雑」に振り分けます。
1つの規程の1つの事実を聞く質問は単純なRAGで速く答え、論点が複数ある・改定や適用範囲の確認が必要な質問だけエージェントに回します。
振り分けに失敗したときは、取りこぼしを避けるためエージェントに回します。

エージェントの流れ（`backend/app/agent.py`）:

1. **plan** 質問を1〜3個の検索クエリに分解する
2. **search** 各クエリでハイブリッド検索し、新しい文書だけを集める
3. **judge** 根拠が足りるか判定し、足りなければ新しいクエリで 2 に戻る（最大3回）
4. **answer** 集めた文書だけを根拠に、出典番号つきで答える

## Azure OpenAI Decisions API の活用（任意）

[Decisions API](https://dev.classmethod.jp/en/articles/azure-openai-decisions-api-ga/) は2026年10月に正式リリースされた、文章を生成せずに**確率つきの型付きの答え**（はい/いいえの確率、選択肢ごとの確率）だけを返すAPIです。
このプロジェクトでは、エージェントの中の「判断」だけを担当させています。

| 使う場所 | 従来（LLMにJSONで答えさせる） | Decisions API |
| --- | --- | --- |
| 振り分け | `{"route": "simple"}` を生成して読む | `complex` である確率を受け取り、しきい値（既定0.4）以上ならエージェントへ |
| 根拠が足りるか | 判定と追加クエリを毎回生成 | 「十分」である確率が0.7以上なら追加クエリの生成を省略。足りないときだけLLMで追加クエリを作る |

ねらいは、判断の部分を「生成してJSONを読む」から「確率で分岐する」に変えることです。

- **しきい値で調整できる：** 取りこぼしを減らすか、速さを取るかを、プロンプトを変えずに数値で調整できる
- **壊れたJSONの心配がない：** 出力が最初から型付きなので、読み取りに失敗しない
- **出力トークンが課金されない：** 判定のための生成がなくなる

応答の速さについては、公開されている計測（日本からアメリカ東部へのテキスト判定で約1.4〜2.1秒）を見るかぎり、短いJSONを返すLLM呼び出しより速くなるとは限りません。効果は評価で確かめます。

有効にするには、gpt-6-luna をデプロイしたリソースの情報を `.env` に設定します（未設定なら従来の方法で動きます）。

```bash
AZURE_DECISIONS_ENDPOINT=https://<gpt-6-luna のリソース>.openai.azure.com
AZURE_DECISIONS_API_KEY=...
AZURE_DECISIONS_DEPLOYMENT=gpt-6-luna
ROUTE_COMPLEX_THRESHOLD=0.4
JUDGE_SUFFICIENT_THRESHOLD=0.7
```

gpt-6-luna は使えるリージョンが限られるため、検索や回答用のリソースとは別のリソースに置けるようにしています。

**状況（2026年11月7日）：実APIでは未計測です。** Azure の無料試用版サブスクリプションでは、gpt-6-luna のクォータがすべてのリージョンで0で、デプロイできませんでした（Japan East で利用できるモデルの一覧には含まれています）。
コードは偽のHTTP応答を使ったテストで動作を確認していますが、リクエストとレスポンスの形は公開記事の例をもとにしたもので、実APIとの一致は確認できていません。未設定のときは従来のLLMによる判定で動くため、上の評価結果はすべて従来の方法によるものです。

## 速度の計測と改善

各段階（振り分け・計画・検索・判定・回答）の所要時間を記録し、画面と評価結果に出しています。

- 複数の検索クエリは、まとめて1回でベクトル化し、検索は並列に実行する（以前は1クエリずつ順番に処理していた）

計測の結果、**並列化の効果はほとんどありませんでした**（エージェントの平均 10.8秒 → 10.4秒）。段階ごとの時間を見ると、検索はもともと短く、時間の大半はLLMの呼び出しでした。

| 段階（エージェント型RAG・検索5件） | 計画 | 検索 | 判定 | 回答 |
| --- | --- | --- | --- | --- |
| 平均時間 | 2.98秒 | 0.59秒 | 3.76秒 | 3.01秒 |

速くするなら、検索ではなくLLMの呼び出し（特に一番長い「判定」）を減らす必要があります。その手段として Decisions API を組み込みましたが、下記の理由でまだ計測できていません。

## 評価

`eval/eval_set.jsonl` の40問で、単純なRAG・エージェント型RAG・自動モードを比べます。
本番に近づけるため、文書には「惑わせる文書」も混ぜています（子会社の規程、廃止済みの旧版、改定前のまま残っているFAQ、検討中の事項が書かれた議事録）。

| 種類 | 問題数 | 例 |
| --- | --- | --- |
| 1つの文書で答えられる | 17 | 経費の申請期限はいつまで？ |
| 複数の文書をまたぐ | 8 | 海外出張で社用携帯も使いたい。何をいつまでに申請する？ |
| 規程の改定を反映する必要がある | 2 | 在宅勤務手当はいくら？（2026年10月に増額） |
| 惑わせる文書がある | 9 | 本社の社員だが、副業は届け出るだけで始めていい？（届出制は子会社の規程） |
| 文書に答えがない | 4 | 退職金はどうやって計算される？ |

測るもの: 正答率（LLMによる採点）、出典の正しさ（正解の根拠になる文書を出典に含めたか）、平均応答時間、平均トークン数、自動モードの振り分け先。

```bash
cd backend
python -m scripts.run_eval            # 結果は eval/results.md に出力（公開する結果は eval/results/ に日付つきで保存）
python -m scripts.run_eval --top-k 3  # 検索件数を絞った、より厳しい条件
```

Windows では、取り込みと2条件の評価を `powershell -ExecutionPolicy Bypass -File backend\scripts\run_all.ps1` でまとめて実行できます。

### 結果

2026年11月7日、40問で計測しました（検索の並列化と、計画のクエリ上限3→5件を入れた後）。結果の全文は [`eval/results/`](eval/results/) にあります。

| 検索件数 | モード | 正答率 | 出典の正しさ | 平均応答時間 | 平均トークン |
| --- | --- | --- | --- | --- | --- |
| 5件 | 単純なRAG | 92%（37/40） | 92%（33/36） | 3.2秒 | 659 |
| 5件 | エージェント型RAG | **100%（40/40）** | **100%（36/36）** | 10.4秒 | 2,317 |
| 5件 | 自動（振り分け） | 98%（39/40） | 97%（35/36） | 8.7秒 | 1,661 |
| 3件 | 単純なRAG | 92%（37/40） | 86%（31/36） | 3.0秒 | 527 |
| 3件 | エージェント型RAG | **100%（40/40）** | **100%（36/36）** | 10.2秒 | 1,849 |
| 3件 | 自動（振り分け） | 98%（39/40） | 97%（35/36） | 9.1秒 | 1,327 |

「惑わせる文書」がある9問に絞った正答率:

| 検索件数 | 単純なRAG | エージェント型RAG | 自動（振り分け） |
| --- | --- | --- | --- |
| 5件 | 78%（7/9） | 100%（9/9） | 89%（8/9） |
| 3件 | 78%（7/9） | 100%（9/9） | 89%（8/9） |

分かったこと:

- **差が出るのは、惑わせる文書がある質問と、複数の文書をまたぐ質問。** 1つの文書で答えられる17問は、3モードとも全問正解でした。単純なRAGは、子会社の規程を本社の規程として答えたり（q31）、改定のお知らせを拾えず古い金額で答えたり（q03）しました。
- **エージェントは精度が高いが、時間は約3.3倍、トークンは約3.5倍かかる。**
- **自動モードは、精度をほぼ保ったままトークンを約28%減らした。** 40問中26問を単純なRAGに回しています。ただし応答時間の短縮は1〜2秒にとどまりました。時間の大半は複雑な質問にかかっており、振り分けにもLLMを1回使うためです。
- **自動モードの取りこぼしは振り分けの誤り。** q36（惑わせる文書あり）を「単純な質問」と判定して単純なRAGに回し、不正解になりました。エージェントで答えれば正解する問題です。
- **出典の正しさは、正答率より差が大きい。** 単純なRAGは答えが合っていても、根拠として不十分な文書を出典にしていることがありました（q36・q37）。

注意点:

- 同じ条件で実行しても、1問程度は結果が変わります（例: 単純なRAGの検索5件は11月5日に95%、11月7日に92%）。数値は1回の計測の結果です。
- 採点も gpt-4.1-mini が行っているため、目安として見てください。

精度を上げるために行った改善（評価で原因を特定してから修正）:

1. 追加検索で見つけた文書が、回答に渡す文書の上限（先頭8件）からはみ出して使われていなかった。各クエリの上位から順に取るようにし、上限を12件にした
2. 改定のお知らせは変更点しか書いていないため、条文の言葉（「モニター」など）で検索すると上位に出なかった。取り込み時に、参照先の条文を検索用の文脈として付けるようにした（LLMには渡さない）
3. 金額・期限・条件を聞く論点では、計画の段階で「〇〇 改定」の検索も行うようにした

評価セットの修正履歴:

- 40問版で、採点プロンプトに「正解と矛盾しない補足は減点しない」を加えました。

計測はすべて gpt-4.1-mini（Azure OpenAI, japaneast）。採点も同じモデルで行っているため、数値は目安です。

## ローカルで動かす

必要なもの: Python 3.11+、Node.js 20+、Azure OpenAI と Azure AI Search のリソース

```bash
# 1. バックエンド
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env   # キーとエンドポイントを記入
set -a && source .env && set +a

# 2. 文書を取り込む（インデックス作成→ベクトル化→登録）
python -m scripts.ingest --docs ../data/docs

# 3. API を起動
uvicorn app.main:app --reload

# 4. 別のターミナルでフロントを起動 → http://localhost:5173
cd frontend && npm install && npm run dev
```

テスト（Azure 不要）: `cd backend && pytest -q`

評価: `cd backend && python -m scripts.run_eval`

## デプロイ

1. Azure にリソースグループを作る（例: `az group create -n rg-aks-demo -l japaneast`）
2. GitHub Actions 用に OIDC でログインできるアプリ登録を作り、リポジトリの Secrets に
   `AZURE_CLIENT_ID` `AZURE_TENANT_ID` `AZURE_SUBSCRIPTION_ID` を、Variables に `AZURE_RESOURCE_GROUP` を登録する
3. Actions の「Deploy」を手動実行する
4. 初回は ghcr.io のパッケージ `agentic-knowledge-search-api` を Public にする（Container Apps が取得できるように）
5. 文書の取り込みはローカルから `python -m scripts.ingest` を実行する
